# Data pipeline

The data layers, the collator and the precompute worker, and the worker CLI. Back to [`CLAUDE.md`](../../CLAUDE.md).

## Worker commands

```sh
yarn workspace @mtg/worker cli sync:catalog      # Oracle Cards → cards, card_names, functional twins (skips if Scryfall's file is unchanged; --force)
yarn workspace @mtg/worker cli sync:printings    # All Cards → English paper printings, sets, card_stats (staple score), cheapest prices, flavor names (after sync:catalog)
yarn workspace @mtg/worker cli sync:tags         # Oracle Tags → tags, tag_edges, tag_closure, card_tags (after sync:catalog)
yarn workspace @mtg/worker cli sync:spellbook    # Commander Spellbook's combo export → spellbook.combos, spellbook.features, raw (skips if the export is unchanged; --force)
yarn workspace @mtg/worker cli sync:typesense [--rebuild]  # drain public.search_index_queue into the search index (--rebuild: every collection from scratch, alias swapped when done)
yarn workspace @mtg/worker cli sync:edhrec [--limit N]    # EDHREC's commander pages → raw edhrec.commanders, edhrec.commander_cards (~3.5 h at 1.5 s a page; --limit: a trial run the collator ignores)
yarn workspace @mtg/worker cli collate [--force] [--only archidekt,user,edhrec,spellbook,...]  # raw sources → corpus: only what changed since each source's last collation (--force: everything, and the removal gate lets a big drop through)
yarn workspace @mtg/worker cli aggregate:corpus  # the full rebuild: the collated corpus.decks → commander_keys, commander_stats, card_global_stats, commander_card_stats, then every score (skips while unchanged; --force re-runs; never writes from an empty corpus; run `collate` first)
yarn workspace @mtg/worker cli precompute [--part commanders,baseline,scores,substitutes,roles,combos,pairs,global-pairs] [--full] [--force]   # the serving tables (T055): without --part, each part that skips itself while its inputs haven't moved (--full adds the nightly baseline and the corpus's card pairs and rebuilds every list)
yarn workspace @mtg/worker cli eval:holdout [--candidate file.json] [--time-split [--snapshot-month YYYY-MM]]   # the offline evaluation (T058): grades adds, cuts and collection mode on held-out decks; with a candidate (scoring and corpus settings over today's) runs both and applies the gate, exiting 1 when it fails. Reads only; report in $MTG_DATA_DIR/reports
yarn workspace @mtg/worker cli serve [--once]    # the VPS worker (T066, deploy/worker/): deck lookups through the crawl, the daily crawl, collation, the precompute passes, weekly EDHREC, as app_config.worker schedules them (--once: one pass)
yarn workspace @mtg/worker cli:hosted <command>  # any worker command against the hosted database: loads apps/worker/.env.hosted (copy .env.example); plain `cli` always means local
```

## Data pipeline

### Data layers

Built 2026-10-05 (T053, migration `20261005000200_data_layers.sql`); `docs/roadmap/card-graph-plan.md` ("Data layers") is the design.

- **Raw, one private schema per source, as the source published it:** `archidekt` and `moxfield` (`decks`), `edhrec` (`commanders`, `commander_cards`), `spellbook` (`combos`, `features`). Raw rows use the source's own identifiers (oracle ids, names, printing ids), so nothing in raw depends on our catalog.
- **`crawl`:** the crawl engine's machinery (`runs`, `state`, `queue`) and the `crawl.decks` view over every deck source's raw table, with the source as a column.
- **`corpus`, collated:** resolved to our card ids: `corpus.decks` (every deck source, with a `source` column), `corpus.edhrec_commanders` and `corpus.edhrec_commander_cards` (EDHREC only), `corpus.spellbook_combos` (Spellbook only), plus `corpus.dirty_commanders` and `corpus.collate_state`. Written only by the collator (`cli collate`, below).
- **`public`:** the serving tables the app reads: the per-commander stats and the baseline (`commander_keys`, `commander_stats`, `commander_card_stats`, `card_global_stats`, `corpus_identity_stats`) and the scores, substitutes, roles and combo pieces built on them, all written by the precompute worker (T055, below) or by `aggregate:corpus`, the full rebuild.
- **Names say whose data a table holds.** A table with one source's rows names that source in its schema (raw: `archidekt.decks`) or in its name (`corpus.edhrec_commanders`), and has no `source` column. A table that mixes sources has a generic name and a `source` column (`corpus.decks`, `crawl.runs`). Columns, functions and fetch commands follow the same rule (`crawl.queue.edhrec_deck_count`, `commander_sets.edhrec_floor`, `sync:edhrec`); `data-layers.sql` checks it. The card catalog is exempt (owner decision 2026-10-05): `cards`, `printings`, `tags` and the rest are our own catalog built from Scryfall, keyed by our ids, and keep their names, as does the `oracle_tags` sync job.
- **Each table has one writer, and each layer reads only the one before it.** None of these schemas is on PostgREST's exposed list; API roles reach them only through security-definer functions.
- **The collator** (`cli collate`, `apps/worker/src/jobs/collate.ts`, T054; sync job `corpus_collate`) writes `corpus` from raw, one source at a time, each in its own transaction:
  - **Decks** (`archidekt`, `moxfield`, `user`): cards are looked up in SQL (oracle ids for raw decks, card ids for players' decks) and the corpus rule runs in TypeScript ([`recommendations.md`](recommendations.md), "Deck corpus and play rates"). Only decks written since that source's last collation are read, less a 15-minute overlap for writes in flight; when `catalog_epoch()` moved, every deck the corpus lacks is retried. A crawled deck gone from raw leaves the corpus; a player's deleted deck leaves through its foreign key.
  - **EDHREC** and **Spellbook** are collated after each successful fetch (`edhrec_pages`, `spellbook_combos`), never from raw without one. Spellbook is also redone on a newer catalog (it is one SQL statement); EDHREC waits for its next weekly fetch.
  - **Where each source got to** is `corpus.collate_state`, written in the same transaction as its rows, so a failed source starts again from the same place.
  - **A source whose collation would remove more than `app_config.corpus.collateMaxRemovedShare` of its rows refuses** (25 removals or more), and an empty raw source is never collated, so a raw table emptied by mistake can't empty the corpus. `--force` re-reads everything and lets the gate pass.
  - **Every write to `corpus.decks` queues its commanders** in `corpus.dirty_commanders` (statement triggers; a security-definer function, since a player deleting their own deck cascades there as that player). EDHREC changes queue their commanders too. The precompute worker's per-commander pass reads the queue (below).

### Precompute worker (T055)

Built 2026-10-06 (migrations `20261005000900`, `20261005001000`); `docs/roadmap/card-graph-plan.md` ("Precompute worker") is the design. `cli precompute` (`apps/worker/src/jobs/precompute*.ts`) builds what the recommendations read; `cli serve` runs its parts on the `app_config.worker` schedule and deck lookups run the per-commander pass. Each part is its own sync job, stages its rows, diffs them against the live ones and writes only what moved.

- **Per commander** (`precompute_commanders`, after each collation): the commanders queued in `corpus.dirty_commanders` get `commander_keys`, `commander_stats` and `commander_card_stats` rebuilt from their own decks (`lib/key-stats.ts`, which `aggregate:corpus` runs too), shrunk toward the last baseline, then their scores and those of every pair they lend decks to. Queue rows go by `seq`, so a commander queued again meanwhile stays queued; a pass takes at most 2,000.
- **Nightly baseline** (`precompute_baseline`, at `baselineHourUtc`): `card_global_stats` and `corpus_identity_stats` summed from the per-commander stats (every counted deck belongs to exactly one key), every commander's shrunk inclusion against it, then every score. Its gate refuses a corpus under 80% of the last run's decks. Over the whole local corpus the per-commander pass and the baseline wrote exactly what `aggregate:corpus` writes (0 rows changed, 2026-10-06).
- **Scores** (`precompute_scores`): `commander_card_scores`, one row per commander (or pair) and card a source deck ran, keyed by the commander cards (`commander_2` 0 for one): every key, and every commander of a pair on its own, with sources picked by `pickCorpusSources`. A row holds the weighted counts the request rebuilds the rates from, `pool_score` (the add pool's order, as `rec_add_candidates` made it) and the final corpus component. `partner_card_totals` holds each partner-capable commander's counts over every key it leads or shares, at full weight, so a pair no key knows is combined exactly (`partnerRowSums`). The arithmetic is `@mtg/core/scoring` `serving.ts`, which the request uses for a card with no row. A changed `app_config.corpus` re-scores everything. **The EDHREC prior** (T061, migration `20261006000500`): for a commander set with an EDHREC page, a card's inclusion is shrunk toward the page's rate when it lists the card (strength: the card's potential decks) or toward min(p0, the page's lowest listed rate) when it doesn't (strength: the page's decks), both capped at `app_config.corpus.edhrecPriorCap` (100, set by the evaluation; 0 turns it off), and the commander's evidence is its decks plus that strength (`cardPrior`, `servedCardRates`). Rows store the page's rate and potential decks per listed card (`prior_rate`, `prior_decks`) and `commander_sets` the page's floor and size, so the request redoes the arithmetic; every single commander with a page is scored, decks or not, but a pair no key knows stays combined from its partners' totals without the prior. EDHREC's numbers are never displayed: the evidence shown is our counts. `commander_sets` (`service_role` only) records for every set it scores whether cards to add draw on its decks (`use_commander`: they earn a share of the score) and whether any decks count at all (`has_sources`: the rater and commander pages), so a request's pool needs nothing read before it.
- **Derived pairs** (T070, migration `20261008000100`): a pair whose own key has fewer than `minDecks` decks borrows every other key of either partner (`isDerivedPair`), so storing its scores copied each partner's decks once per pairing (3.4M of 5.76M rows locally). It stores no `commander_card_scores` rows: `commander_sets.derived` marks it, `commander_pair_pool` holds its first `app_config.precompute.pairPoolDepth` (650: `poolCards` plus `deckCards`) cards by `pool_score` among those a pool may hold (live, legal, not a basic land, in its colours), and `commander_card_priors` every card its EDHREC page lists (both `service_role` only). `serving_cards` returns its own key's counts (`own_decks_with`, `own_too_early`, 0 for a card the key never ran) beside both partners' totals, and the request combines them (`derivedPairRowSums`: own + w·(totals − 2·own), since each partner's totals hold the pair's own key), which is exactly what `pickCorpusSources` sums: rankings are unchanged. Trade-off (owner, 2026-10-07): in 'only' mode a derived pair sees the collection's cards within its stored pool only, then the colours' pool. `pairPoolDepth` 0 or absent turns it off, and the next full scores pass (it re-scores when the depth moves) puts the rows back. Caching popular pairs stays open (T070).
- **Substitutes** (`precompute_substitutes`): `card_substitutes`, for every colour identity that can hold a card (the masks containing its own: 16 for a mono-coloured card, 1 for a five-colour one), the first `substitutesDepth` (`app_config.precompute`, 220) candidates in `rec_swap_candidates`' pool order, and the first 220 that aren't Game Changers. A deck's swap list is the first N of that order inside its colours after its own cards and, in a bracket that allows none, Game Changers are left out, so 220 reproduces every collection-less list exactly (migration `20261006000100`). The first version stored the top 220 in the card's own colours plus the top 220 overall, which missed candidates a multicolour deck should see (3 of 170 hosted swap lists differed). The similarity is computed once per card (`precompute_substitutes`, the same SQL as `rec_swap_candidates` without a deck). A card's list is rebuilt when `substitute_targets.tags_hash` moves (its functional tags and their idf, colours, mana value, twin, the depth, the functional tag config), when a tag near its own is switched on or off, and every `substitutesRebuildDays`. The worker spends at most two minutes a pass on them, so the first build (about 17 minutes locally) spreads over several passes.
- **Roles and combo pieces** (`precompute_roles`, `precompute_combos`): `card_roles` as `rec_card_roles` answered (disabled tags left out), rebuilt when the roles, the kill switch or the tags change; `spellbook_combo_pieces` and `spellbook_combo_details` (results and template pieces, T060) after Spellbook's collation, `service_role` only: the app reads them through `serving_deck_combos`.
- **Card pairs and deck affinity** (`precompute_pairs`, `precompute_global_pairs`; T064, migrations `20261006000900`–`001000`): `commander_card_pairs` per commander key and `card_pairs` over the whole corpus, the pairs of cards decks run together more than chance would have them (`card_a` < `card_b`, positive associations only), counted in memory by `@mtg/core/scoring` `pairs.ts`: lift = (n_ab + prior) / (n_a·n_b/n + prior) with prior = α·max(n_a, n_b)/n over the decks that could have run both (release-aware per key, colour-aware for the corpus), kept above `app_config.pairs.liftFloor` (1.5, owner decision 2026-10-06) with enough support and among either card's `maxPartners`. A key's pairs are recounted when its stats move (after each collation; settings are compared with their keys sorted, since jsonb reorders them); the corpus's every `app_config.worker.globalPairsEveryDays` (7), in the background so lookups don't wait, with a dense counter over cards in `globalMinDecks` decks (16 s and a 380 MB counter, about 1.1 GB peak memory, locally), refusing a corpus under 80% of the last run's decks or a count that doubles the table (`--force` only from the CLI). `serving_deck_affinity` reads the pairs touching a deck's cards, the cards' weights and the `affinity.neighbours` (100) cards those pairs point to most, which join the add pool. The `deck` score component (`affinity.ts`): idf-weighted pmi to the deck's cards, the key's pairs backed off to the corpus's by the card's decks (`affinity.backoffBeta`), scaled by `affinity.halfValue`; suggestions name the deck cards it pairs with (`pairedWith`). `LOW_AFFINITY` cuts sit behind `affinity.lowAffinityCuts`.
- **Every read a recommendation makes goes out in one round.** `serving_add_pool`, `serving_swap_candidates` and `serving_cards` take the deck's commander ids and work out the rest themselves (the commander set, its colours, its pool from `commander_sets`), and return each card whole as a `serving_card` row: the `CARD_COLUMNS` fields, its stored counts for those commanders (a pair no key knows gets its partners' totals), its baseline, release month and roles. Nothing waits on another call's answer, so add, cut and swap each send their reads at once ([`web-platform.md`](web-platform.md), "Transport"). No script counts rounds since `serving-parity.ts` retired with the old path, so check a new read by hand. Keep it that way: a new input goes into these functions or the cached settings, not into a read ahead of them.
  - **What an anonymous caller may ask for is clamped** (`app_config.serving_limits`, migration `20261007000100`): `serving_build_pool` and `serving_deck_affinity` answer one jsonb value, which PostgREST's row cap doesn't limit, so pool size, card lists, a collection and pair neighbours are cut to `poolCards`, `deckCards`, `collections.maxEntries` and `scoring.affinity.neighbours`.
  - They apply the deck's colours, exclusions, Game Changers and legality against `cards` (`cards_rec_pool`), so those are always current. A pair no key knows gets two pools, `partners` and `baseline`, and the app picks one with `commanderShare`, so that rule is never copied into SQL. The pools behind `serving_add_pool` (`serving_commander_pool`, `serving_baseline_pool`, `serving_partner_pool`) are internal: API roles can't run them.
  - Their plans can't see the arguments either: `serving_baseline_pool` runs with `enable_nestloop = off` as the rec functions do, `serving_cards` and `serving_commander_pool` with it on (repeat the SET on any `create or replace`), and `serving_swap_candidates` materializes its matches and their tags, which otherwise were aggregated again for every candidate (about 200 ms for 220).
  - `serving_swap_candidates` returns `rec_swap_candidates`' columns plus the slugs and labels of the tags its matches name, worked out for the candidates it returns and never stored. The mana value term's exponent stops at -700 there: Postgres raises on an underflowing `exp()`, which Gleemax (mana value 1,000,000) did as a target.
- **The only request path the app knows.** `app_config.recs.servingReads` switched it on in production after hosted parity (2026-10-07; `serving-parity.ts` compared both paths until then). The scoring pipeline release removes the old path from the code but leaves `rec_add_candidates`, `rec_swap_candidates`, `rec_card_roles`, `rec_timeouts` and the `recs` row in the database, because its migrations go out before its code and the previous build still falls back to them; a later migration drops them (T067).
- **Size, locally (2026-10-06; scores 2026-10-08):** 2.37M score rows for 4,819 commander sets, 1,790 of them EDHREC pages with no decks of ours (333 MB after `vacuum full`; 5.76M rows and 810 MB before derived pairs), 664k pool rows and 294k EDHREC listings for 1,023 derived pairs (97 MB), 15.7M substitute rows (1.15 GB: about 510 per card since they are stored per colour identity, and the largest table), 389k partner totals (28 MB), 394k combo pieces (56 MB), 763k commander card pairs for 1,314 keys (94 MB) and 470k corpus pairs (79 MB). A full scores pass takes about 2 minutes, 44 s when nothing moved.
